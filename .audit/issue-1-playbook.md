# Issue 1 验收流程

完成标准。issue 1 里每一条范围内的用户故事，要么有一条从命令打进去、用查询或结算记录对上字面结果的测试，并且编辑模式整包通过，要么在决策记录里写明推迟和理由。规则代码不调用 Unity 场景、场景时间和 UnityEngine.Random。表现层以后只发命令、发查询、读结算记录。

规模。规则和测试大约 6300 行 C#，用户故事 100 条，编辑器 6000.6.0f1 已就绪。工作区还有未提交改动，基线按当前工作区测，不按最后一次提交。

严格程度。高。命令、查询和结算记录是表现层要绑的缝，改错会让后面的画面接不上。状态主人、收支主人和一局用语已经记在 ADR 里，这次不重开。

顺序。

1. 用现成编辑模式测试跑一遍，记下通过和失败。这是改之前的基线。
2. 四路只读核对，各看各的文件，不改代码。
   - 开局、关卡、扣除、加班、工资、胜负。
   - 结算时钟、技能、工具、落地、换位、消灭。
   - 培育、科技、商店、技能槽、区域占用。
   - 命令、查询、结算记录，以及有没有把 Unity 漏进规则。
3. 把对得上规格、对不上规格、测试盖不住的故事列成表。只修有代码证据的违背和会让表现层接错的缝。
4. 一次只改一个缺陷。先补会失败的行为测试，再改规则，再跑这组测试。失败就撤回这一条。
5. 整包编辑模式测试再跑一遍。
6. 核对决策记录和这次对话是否一致，再请另一个模型看记录里证据弱的地方。
